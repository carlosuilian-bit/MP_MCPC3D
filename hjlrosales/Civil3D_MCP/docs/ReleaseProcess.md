# Release Process

How a release is cut, from version bump to published artifacts. The platform stops
at **Release Candidate 1** (`1.0.0-rc.1`) for this cycle; the same process applies to
stable releases and subsequent RCs.

---

## 1. Versioning rules (SemVer 2.0.0)

- `MAJOR.MINOR.PATCH[-prerelease][+build]`.
- **Major** bump: breaking protocol change or breaking API change. The bridge/server
  protocol major must match on the wire (`handshake` refuses incompatible majors).
- **Minor** bump: backward-compatible feature (new tool, new option).
- **Patch** bump: backward-compatible fix.
- Pre-release labels for this project: `-alpha.N`, `-beta.N`, `-rc.N`.
- Release tags: `v<version>` (e.g. `v1.0.0-rc.1`).

**Single source of truth:** `eng/version.json`. Never hand-edit the version in
`Directory.Build.props`, `package.json` or `PackageContents.xml`.

---

## 2. Cut a release

### Step 1 - bump

```bash
node eng/scripts/sync-version.mjs 1.0.0-rc.1
```

This rewrites:

- `Directory.Build.props` (Version / AssemblyVersion / FileVersion / InformationalVersion)
- root + server `package.json`
- `packaging/Civil3D.Bridge.Bundle/PackageContents.xml` (AppVersion)
- shipped + sample `bridge.config.json` (`bridgeVersion`) and `server.config.json` (`clientVersion`)

### Step 2 - changelog

Add a `CHANGELOG.md` entry for the new version (keep-a-changelog format) and move
older unreleased items under it.

### Step 3 - commit + tag

```bash
git add -A
git commit -m "release: v1.0.0-rc.1"
git tag v1.0.0-rc.1
git push origin main --tags
```

### Step 4 - let the pipeline run

`.github/workflows/release.yml` (trigger: `v*` tag) performs:

1. **Quality gates** - Node build/test/lint/pack, .NET core build/test, E2E.
2. **Bridge bundle** (self-hosted `civil3d` runner or maintainer-run locally):
   `node eng/scripts/build-bridge-bundle.mjs` -> zip + folder.
3. **npm publish** - `npm publish` (requires the `NPM_TOKEN` secret; skipped when
   the secret is absent or the version already exists).
4. **GitHub Release** - notes generated by `eng/scripts/release-notes.mjs`, artifacts
   attached (bridge bundle zip, npm tarball).

### Step 5 - validate

Run the acceptance checklist in `docs/RELEASE-VALIDATION.md` against the release
artifacts before announcing.

---

## 3. Release notes

```bash
node eng/scripts/release-notes.mjs [version]
```

Combines the matching `CHANGELOG.md` entry with the git log since the previous `v*`
tag, and writes `artifacts/release-notes/<version>.md`. The workflow uses this file
for the GitHub Release body.

---

## 4. Version synchronization guarantees

| Artifact | Value | Source |
| --- | --- | --- |
| .NET assemblies | `Version`/`InformationalVersion` | `Directory.Build.props` |
| npm package | `version` | server `package.json` |
| Bundle manifest | `AppVersion` | `PackageContents.xml` |
| Bridge handshake | `bridgeVersion` | `bridge.config.json` |
| Server handshake | `clientVersion` | `server.config.json` |
| Git tag | `v<version>` | `git tag` |

A CI check (`eng/scripts/quality-gate.mjs`) fails if these drift out of sync.

---

## 5. Hotfixes after a release

1. Branch from the release tag: `git checkout -b hotfix/v1.0.0-rc.1-x v1.0.0-rc.1`.
2. Fix, bump patch (or a new `-rc.2` for RC lines), update `CHANGELOG.md`.
3. Tag + follow the same release flow.

---

## 6. Responsibilities

- **Maintainers**: bump, changelog, tag, publish, validate, announce.
- **CI**: enforced quality gates and artifact generation.
- **Everyone**: report validation failures before the release is announced.
